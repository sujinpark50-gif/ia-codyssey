# 레피 Story Engine

사장님 메모를 재료로 상품에 이야기를 입히는 엔진. 설계 문서 v1.3.1을 실제로 붙여 쓸 수 있는 프롬프트로 정리한 것이다.

원칙: **내용은 메모에 엄격하게, 문장은 손님이 읽기 좋게.**

## 구성

```text
engine/
├── analyzer.md             메모 → 이야기 재료 (글을 쓰지 않음)
├── writer.md               재료 → 헤드라인 + 본문 (기준 샘플 4개 포함)
├── reviewer.md             결과물 ↔ 메모 대조 검사 (글을 쓰지 않음)
├── analyzer.schema.json    각 단계의 구조화 출력 JSON 스키마 (strict 모드용)
├── writer.schema.json
├── reviewer.schema.json
└── README.md
```

## 흐름

```text
Analyzer (메모 + 사진)
  ├─ NEED_MORE_INFO / 사진·메모 충돌 → 질문 최대 2개 → 답변 받아 Analyzer 재실행
  ├─ NO_STORY_FOUND → "상품 특징 중심으로 정리하는 편이 좋아요" 안내
  └─ READY
       → Writer → Reviewer
            ├─ PASS → 결과 표시
            └─ REVISE → Writer 재작성 (review_issues 전달, 1회) → Reviewer → 결과 표시
                        두 번째도 REVISE면 결과는 보여주고 review를 로그로 저장

사장님이 결과를 보고 덧붙인 말 → seller_additions에 넣고 Analyzer부터 다시
```

각 단계는 시스템 프롬프트(`*.md`)와 사용자 메시지(입력 JSON)로 호출한다. 입력 JSON의 필드는 각 프롬프트의 "입력" 섹션에 적혀 있다.

## 설계 문서에서 바뀐 점

설계 문서에 흩어져 있던 규칙을 모델이 헷갈리지 않게 정리하면서 세 가지를 더했다.

1. **Analyzer가 판매자 시점에서 못 쓰는 재료를 미리 분류한다** (`seller_voice_exclusions`). "한 번에 뽑았다", "좋은 추억이었다" 같은 재료를 Writer가 판단하게 두지 않고, 분석 단계에서 걸러서 넘긴다. 권유로 바꿀 수 있는 것은 `convertible_to`에 바뀐 문장을 같이 넘긴다.
2. **Analyzer가 이야기의 출발점을 고른다** (`strongest_material`). Writer의 첫 문장이 인사나 소개가 아니라 가장 강한 재료로 시작하게 하기 위해서다.
3. **`protected_phrases`를 `distinctive_phrases`로 바꿨다.** "보존해야 할 말"이 아니라 "이 상품에만 있는 개성 있는 말"이라는 뜻이 이름에 드러나게 했다. 반말 버릇과 스펙 문장은 여기서 빠진다.

## 모델과 비용

| 단계 | 추천 | 이유 |
| --- | --- | --- |
| Analyzer | 중간 모델 (예: GPT-5.6 Terra) | 분류 작업. 사진을 이 단계에만 보낸다 |
| Writer | 상위 모델 (예: GPT-5.6 Sol) | 결과물 품질이 여기서 결정된다 |
| Reviewer | Writer와 **다른** 모델 | 같은 모델은 같은 실수를 같이 놓친다 |

- 시스템 프롬프트는 매번 같으므로 프롬프트 캐싱을 쓴다. Writer 프롬프트가 기준 샘플 때문에 가장 길다.
- 추론 강도는 설정하지 않는다. gpt-5.4는 기본값이 none이라 이미 가장 낮은 상태다.
- 사진은 긴 변 1568px 이하로 줄여서 보낸다.
- 재작성이 일어나면 Writer와 Reviewer가 한 번씩 더 돌아서 비용이 약 1.6배가 된다. 재작성 비율을 로그로 보면서 프롬프트를 고친다.

## 검증 방법

### 1. 기준 샘플 재현

Writer 프롬프트에 들어 있는 네 샘플(밀짚모자, 쥐꼬리 낚시대, 닉스고, 잉어킹)의 메모를 넣고 돌린다. 기준 결과물에 가까운지 본다. 다만 샘플이 프롬프트 안에 있으므로, 여기서 잘 나오는 건 최소 조건일 뿐이다.

### 2. 새 메모로 일반화 확인 (진짜 검증)

샘플과 겹치지 않는 메모로 돌린다. 특히 이런 종류가 좋다.

- 추억과 무관한 상품 (기능, 맛, 편리함이 중심)
- 전혀 다른 업종 (카페 디저트, 네일 시술, 꽃다발)
- 메모가 아주 짧은 경우 (한두 줄) → NEED_MORE_INFO가 적절히 나오는지
- 메모에 요청문만 많고 재료가 적은 경우

### 3. 확인 항목

- [ ] 메모에 없는 장면이나 손님 반응이 있는가
- [ ] 첫 문장이 인사나 소개 상투구인가
- [ ] 헤드라인의 의미가 본문 마지막에서 반복되는가
- [ ] 같은 동사가 세 번 이상 나오는가
- [ ] 상품명만 바꾸면 다른 상품에도 통하는 문장이 있는가
- [ ] 샘플의 표현("추억템", "사냥 모드", "~해도, ~한다")을 흉내 냈는가
- [ ] 모든 헤드라인이 같은 유형으로 나오는가
- [ ] Reviewer가 위 문제를 실제로 잡아내는가 (일부러 문제 있는 글을 넣어서 확인)

마지막 항목이 중요하다. Reviewer가 통과만 시키면 파이프라인 전체가 의미 없어진다. 앞서 문제가 됐던 쥐꼬리 낚시대 결과물("고양이가 진짜 사냥한다는 게 무슨 의미인지 알게 되는 낚시대…")을 Reviewer에 넣어서 BLOCK과 MAJOR 이슈가 나오는지 먼저 확인할 것.

## 기준 샘플을 추가할 때

사장님이 "이런 느낌"이라고 확정한 결과물만 `writer.md`의 "기준 샘플"에 추가한다. 샘플이 늘수록 프롬프트가 길어지고 비용이 오르므로 5~6개를 넘기지 않는다. 새 샘플은 기존 샘플과 **주제와 헤드라인 유형이 겹치지 않는 것**을 고른다. 겹치는 샘플이 쌓이면 모델이 그 패턴을 규칙처럼 따라 한다.
