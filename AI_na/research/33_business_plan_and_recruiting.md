# I. 사업계획서

## 1. 한 줄로

> **내가 하고 싶은 것을 내비게이션해주면서, 내가 게임 캐릭터처럼 성장하는 스토리.**

풀어 쓰면 이렇다.

> **"물구나무서기 하고 싶은데."**
> 그러면 코어부터 시작하는 계단을 놔준다. 실제로 올라가 본 결과로 그 계단이 다시 그려지고, 그동안 **내 스탯이 오른다.**

**두 개가 한 몸이다.** 내비게이션이 없으면 그냥 게임이고, 성장 서사가 없으면 그냥 계획 앱이다.

### 게임으로 치면

| 빌려온 것 | 어디서 | 우리 버전 |
|---|---|---|
| **자유도** | 마인크래프트 | 목표를 우리가 정해주지 않는다. 뭘 하고 싶든 그게 입구다 |
| **개인 퀘스트 라인** | 에버퀘스트 · WoW | 목표를 선언하면 거기까지 가는 퀘스트가 생성된다 |
| **티어** | 리그 오브 레전드 | 분기 시즌제. 브론즈 → 실버 → 골드 |

**그런데 셋 다 한 발씩 비틀었다.**

- **WoW의 퀘스트는 사전 제작이다.** 모든 유저가 같은 퀘스트를 받는다. 우리 퀘스트는 **매번 생성되고 사람마다 다르다** — 같은 "물구나무서기"라도 플랭크 2분인 사람과 30초인 사람의 1주차가 다르다.
- **롤은 지면 티어가 깎인다.** 우리는 안 깎는다. 실패는 티어가 아니라 **상태창**을 건드린다.
- **마인크래프트는 아무것도 안 알려준다.** 우리는 자유도는 그대로 두되 **길은 놔준다.**

**그리고 셋 다에 없는 게 하나 있다.**

> 게임의 스탯은 올라가기만 한다.
> **우리 상태창은 내려간다** — 시스템이 자기 판단이 틀렸다고 인정할 때.

## 2. 문제

하고 싶은 게 생겼는데, 어디서부터 시작해야 할지 모른다.

**"물구나무서기 하고 싶은데"** 라고 검색하면 나오는 건 전부 **물구나무서기 하는 법**이다. 벽에 다리 올리고, 손 짚고, 균형 잡고. 그런데 나는 플랭크 30초도 못 버틴다. **그 영상은 나를 위한 게 아니다.**

목표 관리 앱에 입력해도 똑같다. 목표를 넣으면 **누구에게나 같은 단계**를 준다. 코어가 이미 강한 사람과, 팔굽혀펴기 5개가 한계인 사람에게 **같은 1주차**가 나온다.

그리고 3일 뒤 못 따라가면 앱은 이렇게 반응한다 — 일정을 뒤로 민다. 알림을 보낸다. 스트릭이 끊긴다.

**아무도 "왜 못 했는지" 묻지 않고, 아무도 "처음 판단이 틀렸을 수 있다"고 생각하지 않는다.**

사용자는 자기가 게으르다고 결론 내리고 앱을 지운다.

## 3. 해결 — 네 단계 루프

| 단계 | 하는 일 | 화면 |
|---|---|---|
| ① **의도 → 목적지** | 막연한 말을 목표로 만든다 | 대화형 온보딩 |
| ② **현재 위치 진단** | 목표 대비 지금 어디인지 **재본다** | 진단 질문 + 짧은 실측 |
| ③ **개인 경로 계산** | ①과 ② 사이를 잇는 계단을 놓는다 | 퀘스트 목록 |
| ④ **실행 결과로 교정** | 실제로 해본 결과로 **②를 고치고 ③을 다시 만든다** | **상태창** |

**④가 이 제품의 전부다.** 나머지 셋은 이미 시장에 다 있다.

### 물구나무서기로 보면

```
① 목적지    "물구나무서기 하고 싶은데"
             → 목표: 벽 없이 물구나무 10초

② 진단      "플랭크 몇 초 버티세요?"     → 30초
             "팔굽혀펴기 몇 개 하세요?"   → 8개
             "벽 짚고 물구나무 되세요?"   → 못 해요

             상태창 생성
               코어 지구력  : 30초  (약함)
               상체 근력    : 8개   (보통)
               역위 적응    : 없음

③ 경로      1주차  플랭크 30초 × 3세트 / 데드버그
             2주차  플랭크 45초 / 파이크 푸시업
             3주차  벽 짚고 물구나무 10초
             ...
             8주차  벽 없이 물구나무 10초

④ 교정      1주차 Quest: "플랭크 45초 유지"  →  2회 실패
             ↓
             코어 지구력: 30초 → 25초 (하향)
             변경 사유: "플랭크 45초 Quest 2회 실패 (8/25)"
             ↓
             경로 재계산: 2주차를 플랭크 35초로 낮추고,
                          데드버그 1주 더 붙임
```

**사용자를 탓하지 않는다.** "계획을 못 지켰다"가 아니라 **"우리 초기 진단이 틀렸다"** 로 처리한다. 이게 슬로건이 아니라 데이터 구조로 성립한다.

### 도메인을 안 가린다

목표가 무엇이든 같은 루프가 돈다. **상태 필드를 무엇으로 잡을지는 AI가 목표에 맞춰 만든다.**

| 목표 | AI가 만든 상태 필드 |
|---|---|
| 물구나무서기 | 코어 지구력 · 상체 근력 · 역위 적응 · 손목 가동성 |
| **틱톡 챌린지 춤 따라하기** | **구간별 숙련도(1~8박 / 9~16박 …) · 속도 적응 · 동작 연결** |
| 기타로 좋아하는 곡 치기 | 코드 전환 속도 · F 바레 · 스트로크 패턴 · 곡 암기 |
| 토익 800점 | 어휘량 · 문법 정확도 · LC 속도 · 시간 관리 |
| 5km 완주 | 심폐 지구력 · 연속 달리기 시간 · 회복 속도 |

**춤이 이 구조에 특히 잘 맞는다.** 안무는 이미 8박자 단위로 쪼개져 있어서 **상태 필드가 저절로 나온다.** 3구간에서 두 번 막히면 그 구간만 0.5배속 반복을 붙이고 다음 구간을 미루면 된다 — 교정이 눈에 보인다.

**틀은 하나다** — `필드명 / 현재값 / 근거 / 변경시각 / 변경사유`. 그 안을 무엇으로 채울지만 목표마다 달라진다.

## 4. 차별화 — 이 한 문장만 주장한다

> **자기보고된 현재 위치를 실행 결과로 교정하고, 그 교정 이력이 다음 경로 생성의 입력이 된다.**

이 문장이 성립하려면 세 가지가 **함께** 있어야 한다. 하나라도 빠지면 ChatGPT에 프롬프트 넣는 것과 구별되지 않는다.

| 조건 | 뜻 |
|---|---|
| **관찰의 구조화** | 실패가 자유서술 하소연이 아니라, **미리 정해둔 판정 기준에 대한 성공/부분/실패 기록**으로 들어온다 |
| **상태의 구조화** | 자유 메모가 아니라 **조회 가능한 필드** (`코어 지구력: 30초 → 25초`, 변경 시각 포함) |
| **인과의 저장** | "왜 바뀌었는가"가 응답으로 스쳐가지 않고 **저장되어 나중에 조회된다** |

### 판정 기준을 AI가 미리 만든다 — 이게 열쇠다

센서도 없고 채점도 없는데 어떻게 "실행 결과"를 아는가. **Quest를 만들 때 성공 조건을 함께 만들어 두면 된다.**

```
Quest        플랭크 45초 유지 × 3세트
판정 기준    3세트 모두 45초 완주 = 성공
             1~2세트만 완주      = 부분
             45초 도달 실패      = 실패
```

사용자는 **"못했어요"가 아니라 "2세트까지"** 를 누른다. 이게 자유서술과 결정적으로 다른 지점이다. 값이 구조화되어 있으니 **상태 필드를 어느 방향으로 얼마나 움직일지 규칙으로 정할 수 있다.**

## 5. "게임형"이 왜 장식이 아닌가

이 앱은 인생을 RPG처럼 다룬다. 다만 게임 요소를 전부 같은 취급하면 안 된다. **네 층이 있고 역할이 다르다.**

| 층 | 무엇 | 역할 | 판단 |
|---|---|---|---|
| **상태창** | 진단된 상태 필드 + 변경 이력 | **차별화가 눈에 보이는 유일한 지점** | **MUST** |
| **퀘스트** | 경로의 각 단계 | 계획을 「할 일 목록」이 아니라 **「받는 것」** 으로 바꾼다 | **MUST** |
| **경험치 · 레벨 · 티어** | 퀘스트를 해낸 만큼 쌓이는 것 | **해온 것이 남는다**는 감각 | **MUST** |
| 뱃지 · 성장 연출 · 이펙트 | 시각적 보상 | 재미 | SHOULD |
| 페널티 | HP 손실 · 강제 벌칙 | — | **안 한다** |

### 경험치와 티어 — 분기 시즌제

퀘스트를 해내면 **경험치**를 얻고, 쌓인 경험치가 **티어**를 만든다. **티어는 분기 단위로 운영된다.**

| 티어 | 뜻 |
|---|---|
| 🥉 **브론즈** | 시작 구간 |
| 🥈 **실버** | 이번 분기를 꾸준히 밟아옴 |
| 🥇 **골드** | 이번 분기 최상위 구간 |

**경험치 획득**

| 퀘스트 결과 | XP |
|---|---|
| 성공 | 100% |
| 부분 | 50% |
| 실패 | 0 — **깎지 않는다** |

**분기가 바뀌면 새 시즌이 시작된다.** 랭크 게임의 시즌과 같은 구조다.

- **분기 안에서는 절대 내려가지 않는다.** 실패해도, 며칠 쉬어도 티어는 그대로다.
- **분기가 끝나면 티어가 초기화되고 새로 시작한다.** 지난 분기 기록은 **지우지 않고 보관**한다 — `2026 Q1 브론즈 → Q2 실버 → Q3 골드`가 그 자체로 성장 기록이 된다.

**왜 분기인가 (설계 의도)**
- 목표는 대개 8주~3개월 안에 끝나거나 바뀐다. **분기가 목표의 자연스러운 호흡**이다.
- 영원히 누적되면 늦게 시작한 사람이 영영 못 따라잡는다. 시즌제면 **매 분기 모두가 같은 출발선**이다.
- "이번 분기엔 골드 찍자"가 리텐션 훅이 된다.

### ★ 핵심 설계 — 티어와 상태창은 다른 축이다

이 둘을 섞으면 제품이 무너진다. **반드시 분리한다.**

| 축 | 무엇을 나타내는가 | 실패하면 | 분기가 바뀌면 |
|---|---|---|---|
| **상태창** (역량) | 지금 실제로 뭘 할 수 있는가 | **정정된다** (오르내림) | **그대로 간다. 절대 리셋하지 않는다** |
| **티어** (시즌 성과) | 이번 분기에 얼마나 해왔는가 | **안 깎인다** | **새 시즌으로 초기화** (지난 기록은 보관) |

**두 축이 정반대로 움직인다는 게 핵심이다.**

- 실패는 **티어가 아니라 상태창**을 건드린다 — 벌이 아니라 정정이다.
- 분기 전환은 **상태창이 아니라 티어**를 건드린다 — 내가 쌓은 코어 지구력이 분기 바뀐다고 사라지면 말이 안 된다.

플랭크 45초에 두 번 실패해도 티어는 브론즈 그대로다. 시도한 건 시도한 거다. 대신 상태창이 `코어 지구력 30초 → 25초`로 정정되고 계단이 낮아진다.

> **실패했을 때 잃는 건 없다. 다만 지도가 다시 그려진다.**

Habitica는 이 둘을 하나로 묶어서 **실패가 곧 손실**이 된다(HP 감소). 우리가 반대로 가는 지점이 정확히 여기다.

**그리고 삼성과도 갈린다.** 삼성 러닝코치는 재측정하면 **진행 이력이 삭제된다**(6-3항). 우리는 반대다 — **티어는 시즌마다 새로 시작하되, 상태창과 그 변경 이력은 영구 보존한다.** 리셋되는 것과 남는 것이 명확히 갈려 있다.

### 상태창은 UI가 아니라 제품 그 자체다

「나 혼자만 레벨업」의 상태창이 특별한 이유는 화면이 예뻐서가 아니다. **숫자가 실제 행동으로 움직이기 때문**이다. 성진우가 팔굽혀펴기를 하면 근력이 오르고, 근력이 오르면 **다음에 열리는 던전이 달라진다.**

우리가 하려는 게 정확히 그것이다. 그래서 상태창은 부가 화면이 아니라 **홈 1급 화면**이다.

### Habitica와 갈리는 지점

게임화 습관앱의 원형인 **Habitica**(Google Play 설치 500만+, 2015-12-10 출시 — 등급 2)와 비교하면 차이가 선명하다.

| | Habitica | 우리 |
|---|---|---|
| 스탯이 뜻하는 것 | **얼마나 성실했는가**의 누적 | **지금 실제로 뭘 할 수 있는가** |
| 실패하면 | HP가 깎인다. 그리고 과제가 **더 비싸진다** | **계단을 낮춘다** |

Habitica 공식 FAQ 원문: *"Missing Dailies causes you to lose HP, but the more difficult they are, the better the rewards!"* / *"The more red the task, the more Gold and Experience you'll earn for completing it, so be sure to take on even your toughest tasks!"*

**실패가 과제를 쉽게 만드는 게 아니라 비싸게 만든다.** 우리는 정확히 반대로 간다. 이게 슬로건이 아니라 4항의 교정 루프로 성립한다.

### 완성형 — 지금 안 하지만 방향은 여기다

> 언젠가 **AI 안경**을 쓰면 눈앞에 상태창이 뜨고 퀘스트창이 떠서, 진짜 RPG를 하듯 내가 성장하는 것.

**8주 안에는 안 한다.** 하드웨어는 범위 밖이고 시연에도 넣지 않는다. 다만 **이 방향이 지금의 설계를 결정한다** — 나중에 안경으로 옮겨지는 것은 **상태창과 퀘스트창**이지 대시보드나 리스트가 아니다. 그래서 지금 그 둘을 1급으로 만든다.

## 6. 시장 근거 (직접 조사, 2026-08 기준)

경쟁 제품 10개를 공식 자료 원문으로 조사해 14개 항목으로 비교했다.
대상: ATLVL · Attainify · Stepie · DAMI · Ripple AI · Goaltree · 키피 · Maty · Tiimo · 삼성 헬스 러닝코치

### 6-1. 이미 표준이 된 것 — 여기서 싸우면 안 된다

- **「목표를 단계로 쪼개준다」는 10개 중 10개가 한다.** 설치 10명짜리 개인 앱부터 삼성까지 전부.
- 자유 목표 입력 8/10, 목표 구체화 7/10.

**→ 이걸 차별화로 내세우면 즉시 무너진다.** "AI가 계획 짜준다"는 이미 상품이다.

### 6-2. 비어 있는 것

- **미완료 "원인"을 구조화해 묻는다는 서술이 10개 제품의 공식 자료 어디에도 없다.**
- **목표 자체를 재검토하자고 제안한다는 서술도 마찬가지로 없다.**
- 확인된 재계획 트리거는 **전부 정량 신호**였다 — "3회 연속 스킵", "토요일 85% vs 금요일 30%", "부담스러워 보임". **"왜"를 입력으로 쓴다고 밝힌 제품은 없었다.**

> **표현에 주의.** 「아무도 안 한다」가 아니라 **「공식 자료에 그렇게 쓰여 있지 않다」** 까지만 주장한다. 공개하지 않았을 뿐 구현했을 수 있고, 심사에서 반박당하면 나머지 근거까지 같이 무너진다. 확인한 것은 **공개 자료의 부재**이고, 그것만으로도 충분히 세다.

### 6-3. ★ 가장 중요한 발견 — 진단과 교정이 한 제품 안에서 만나지 않는다

| 제품 | 진단 | 교정 | 빠진 고리 |
|---|---|---|---|
| **삼성 헬스 러닝코치** | **최고 수준** — 12분 실측으로 레벨 부여 *(범위 1~10은 언론 보도 기준, 공식 문서 미확인)* | **없음** | 재측정이 수동이고, **재측정하면 기존 진행 이력이 삭제된다** (공식 문서 원문) |
| **Attainify** (설치 5,000+) | 있음 — 목표·경험·사고방식 퀴즈 | 모호 | 무엇을 관찰해 조정하는지 안 밝힘 |
| **Goaltree** | 없음 | **최고 수준** — 재계획 트리거 3개 공개 | 갱신되는 **상태 필드가 없다** |
| **Tiimo** | 사용자가 알려야 함 | **최고 수준** — 분해·이동 제안 | 행동 패턴 학습을 **공식 문서가 "아직 안 했다"고 밝힘** |
| ATLVL | 약함 | 중간 | 체크인은 구조화했는데, 그 값이 **무엇을 교정하는지** 서술이 없음 |

**확인한 10개 모두, 공개 자료 기준으로는 한 고리씩 빠져 있다.**

### 6-3-1. ★ 가장 가까운 경쟁자를 먼저 꺼내놓는다 — ATLVL

**숨기면 심사에서 먼저 무너진다.** ATLVL의 Google Play 설명문에는 우리 차별화 문장과 표층 서술이 거의 같은 문구가 있다.

> `"Adaptive replanning — our smart models read your check-in patterns and restructures your plan, not just your tasks"`
> — ATLVL Google Play 설명문 (등급 2)

반박은 세 조건(4항)으로 한다.

| 조건 | ATLVL | 우리 |
|---|---|---|
| 관찰의 구조화 | **있다** — `done/partial/skip + easy/right/hard` | 사전 판정 기준 |
| 상태의 구조화 | **공개 자료에 서술 없음** — 무엇이 갱신되는지 밝히지 않음 | 상태 필드 |
| 인과의 저장 | **공개 자료에 서술 없음** | 변경 사유 저장·조회 |

**그리고 ATLVL 자신의 공식 문서는 훨씬 약하게 말한다.** 공식 Methodology 원문은 `"That feedback can influence the pacing, difficulty, task type, and next steps."` — **조건부**다. 스토어 문구(단정형)와 공식 문서(조건부)의 강도가 갈린다.

**이건 마케팅 문구이고 구현은 미검증이다.** 같은 기준을 우리에게도 적용한다 — **우리 주장의 근거는 문구가 아니라 9항의 2차 시연 화면**이다.

특히 **삼성이 시사적이다.** 12분 달리기 테스트로 레벨을 실측해 놓고, 정작 훈련을 빠져도 그 레벨은 안 바뀐다. 다시 재보려면 사용자가 버튼을 눌러야 하고, 누르면 **그동안의 진행 기록이 지워진다.** 진단은 최고 수준인데 루프가 닫히지 않는다.

### 6-4. 국내 상황

- 비교 대상 10개 중 국내 직접경쟁 **3건** — DAMI(서울) / 키피(강남) / Maty(개인)
- **전부 초기 단계**: DAMI는 16개월 미갱신에 Google Play 리스팅도 내려감, 키피 설치 10+, Maty 설치 50+
- **10개 전체 기준** 한국어 정식 지원 확인은 4건(국내 Maty + 해외 Stepie·Tiimo·삼성). **한국 특화 기능은 Maty의 사주 추천 1건**뿐

> **하루업(HARU UP)을 왜 뺐나.** 국내 앱이고 조사에서 「직접경쟁 후보」로 분류됐으나, **입력 방식이 자유 입력이 아니라 대·중·소분류에서 목표를 고르는 방식**이다(등급 2 확인). 우리 컨셉의 ①단계(막연한 말을 목표로)와 층위가 달라 상위 10 비교에서 제외했다. **단 캐릭터 성장·레벨업을 갖고 있어 게임 계층 비교에서는 참고 대상이다.**

**→ 국내 시장은 아직 형성되지 않았다.**

## 7. 8주 안에 이걸 어떻게 하는가

범용이라 오히려 유리한 게 있고, 불리한 게 있다. 정면으로 다룬다.

| | 판단 |
|---|---|
| **유리** | 경로와 상태 필드를 **AI가 생성**한다. 도메인별 콘텐츠를 우리가 만들 필요가 없다 |
| **유리** | 시연이 강하다. "물구나무서기"는 심사위원이 3초 만에 이해한다 |
| **불리** | 센서·채점이 없다 → 실행 결과가 **자기보고**다 |
| **대응** | **판정 기준을 Quest와 함께 생성**해 자기보고를 구조화한다 (4항). 완벽한 측정은 아니지만, 자유서술과는 층위가 다르다 |
| **불리** | 목표가 무한하면 품질이 들쭉날쭉해진다 |
| **대응** | MVP는 **시연용 목표 3~5개로 사전 검증**해 두고 출발한다. 입력은 자유롭게 받되, 검증된 목표를 예시로 앞에 세운다 |

**시연 시간 제약이 설계를 결정한다**: Quest 단위를 작게 만들어야 한다. "플랭크 45초 × 3세트"는 5분 시연 안에 결과를 넣을 수 있다. "8주 프로그램 완주"는 안 된다.

## 8. 8주 MVP 범위

### MUST — 이게 없으면 제품이 아니다

1. **대화형 온보딩** — "물구나무서기 하고 싶은데" 같은 막연한 말을 목표로 구체화
2. **진단** — 목표에 맞는 질문 + 짧은 실측으로 **상태 필드 생성**
3. **경로 생성** — 상태 + 목표 → 주차별 마일스톤 + Quest 목록
4. **Quest + 판정 기준** — Quest마다 **성공/부분/실패 기준을 함께 생성**
5. **퀘스트 수락 → 수행 → 결과 보고** 흐름 — 계획을 「할 일 체크」가 아니라 **퀘스트를 받고 보고하는 것**으로 만든다
6. **상태 교정** — 결과로 상태 필드 갱신 + **변경 사유 저장**
7. **경로 재계산** — 갱신된 상태로 다음 구간 재생성
8. **상태창** — **홈 1급 화면.** 필드 값 + 변경 이력 + "왜 바뀌었는지" 조회. **값이 바뀌는 순간의 연출 포함**
9. **경험치 · 티어** — 퀘스트 결과로 XP 적립, 브론즈 → 실버 → 골드. **분기 시즌제**, 실패해도 깎이지 않는다. *(8주 안에 분기가 지나가지 않으므로 스키마에 시즌 개념만 넣고 화면에 「2026 Q3」 표기까지 — 리셋 동작 구현은 SHOULD)*

### SHOULD — 되면 좋다

10. 뱃지 · 레벨업 이펙트 · 성장 연출
11. 상태 변화 그래프
12. 목표 여러 개 동시 진행 (계정 전체 레벨)

### WON'T — 8주 안에 절대 안 한다

- ❌ **AI 안경** (완성형 비전, 지금은 안 함)
- ❌ 웨어러블·센서 연동 (자기보고로 간다)
- ❌ **영상 분석·자세 인식** — 춤이든 운동이든 영상을 뜯어보는 건 8주 밖이다. 사용자가 원본 영상을 보고, 우리는 **연습 계획과 상태 교정**을 맡는다
- ❌ 소셜 · 파티 · 리더보드
- ❌ 캘린더 연동 · 결제 · 푸시 고도화
- ❌ **미이행 페널티** (HP 손실 등) — 이 제품이 명시적으로 안 하는 것

## 9. 시연 — 심사에서 이 두 장면만 보여준다

### 1차 시연 (3분) — 이해용

> 세 사람이 똑같이 **"물구나무서기 하고 싶은데"** 를 입력한다.
>
> - A는 플랭크 2분, 팔굽혀펴기 30개 — **3주차부터 시작**하는 경로
> - B는 플랭크 30초, 팔굽혀펴기 8개 — **코어 기초 4주**가 앞에 붙은 경로
> - C는 손목 통증 이력 있음 — **손목 가동성 루틴**이 먼저 들어간 경로
>
> 같은 목표, 같은 문장. **세 개의 다른 계단.**

**메시지**: "같은 목표라도 현재 위치가 다르면 경로도 달라야 한다."

### 2차 시연 (5분) — ★ 차별화 근거는 이것뿐

> B가 1주차 Quest를 받는다: **"플랭크 45초 × 3세트"**
> → 결과 보고: **"2세트까지"** (구조화된 선택지, 자유서술 아님)
> → 다음 날 같은 Quest: **"1세트까지"**
> → **상태창 값이 눈앞에서 바뀐다**: `코어 지구력 30초 → 25초`
> → 그 항목을 누르면 **"왜 바뀌었는지"** 가 뜬다
>   *"플랭크 45초 Quest 2회 연속 미달 (8/25 · 8/26)"*
> → **경로가 다시 만들어진다** — 2주차 목표를 45초에서 35초로 낮추고, 데드버그 1주 추가
> → **그런데 티어는 그대로다.** 브론즈 · XP 240. *"시도한 건 시도한 거다"*

**이 화면 하나에 세 조건이 전부 보인다** — 구조화된 관찰 / 구조화된 상태 / 저장된 인과.

그리고 이 장면이 말하는 것은 하나다. **"당신이 게을렀던 게 아니라, 우리가 당신을 잘못 봤던 겁니다."**

### 시연 소재 대안 — 춤

물구나무서기 대신(또는 함께) **틱톡 챌린지 안무**로 같은 두 장면을 만들 수 있다. 심사 반응은 이쪽이 더 좋을 수 있다.

> "이 챌린지 따라하고 싶은데"
> → 진단: 춤 경험 없음 / 박자 감각 보통
> → 경로: 안무를 **8구간**으로 쪼개고, 1구간부터 0.5배속으로
> → 3구간 Quest **2회 연속 "동작은 되는데 박자를 놓침"**
> → 상태창: `3구간 숙련도: 보통 → 취약` · `속도 적응: 0.75배 → 0.5배`
> → 경로 재계산: 3구간만 0.5배속 반복 3회 추가, 4구간은 뒤로 밀림

**둘 중 무엇을 1차 시연으로 쓸지는 W7 검증 결과로 정한다.** 물구나무서기는 "몸이 만들어지는" 서사가 강하고, 춤은 **구간 분해가 화면에 그대로 보여서** 이해가 빠르다.

## 13. 미해결 쟁점 — 팀과 함께 정한다

지금 혼자 정하지 않고 남겨둔 것들이다. **모르는 걸 모른다고 적어두는 편이, 나중에 조용히 뒤집는 것보다 낫다.**

### 13-1. 모집 기간이 일정에 없다

8주 일정표는 **W1부터 개발이 시작된다고 가정**한다. 그런데 지금 팀이 없다. 모으는 데 2~3주가 걸리면 실제 개발 기간은 **5~6주**고, 그러면 MUST 9개는 안 들어간다.

**일정을 다시 잡을지, MUST를 줄일지는 인원이 확정돼야 정할 수 있다.** 줄인다면 SHOULD가 아니라 MUST 안에서 골라야 하므로 — 예컨대 경로 재계산(7번)을 수동 트리거로 낮추는 식 — 팀과 함께 결정한다.
→ **담당: 전원 / 시점: 팀 확정 직후**

### 13-2. 운동 목표의 안전 문제

1차 시연 시나리오 C가 **"손목 통증 이력 있음"** 이다. 부상 이력자에게 운동 경로를 주는 것은 **심사에서 반드시 질문이 나온다.**

정해야 할 것 — 면책 문구로 충분한가 / 특정 조건(통증·질환·임신 등)은 아예 거절할 것인가 / 의료 조언의 선을 어디에 그을 것인가. **범용으로 가면 운동만이 아니라 단식·재활 같은 목표도 들어온다.**
→ **담당: R1 + 전원 / 시점: W1**

### 13-3. 미보고를 어떻게 볼 것인가

Quest 결과를 "2세트까지"로 받는 설계는 했는데, **아예 안 누르는 경우가 제일 흔하다.**

미보고를 **실패로 볼지 무응답으로 볼지**에 따라 상태 교정 루프가 돌기도 하고 멈추기도 한다. 실패로 처리하면 바빠서 못 누른 사람의 상태를 잘못 내리고, 무응답으로 두면 이탈한 사람에게 아무 반응도 못 한다. **MUST 5번의 구멍이다.**
→ **담당: R1 · R2 / 시점: W1 (상태 모델 설계와 같이)**

### 13-4. 이중 지표를 사용자가 이해할까

**티어는 오르는데 스탯은 내려가는 화면**이다. 설계 의도는 분명하지만(5항) 사용자가 혼란스러워할 수 있다. 두 축을 화면에서 어떻게 갈라 보여줄지는 만들어봐야 안다.
→ **담당: R3 · R5 / 시점: W6**

### 13-5. 인원별 소요 추정이 없다

`01_PLAN.md`는 **3인/4인/5인 각각의 소요를 따로 추정**하도록 요구한다("하나의 값으로 뭉뚱그리지 않는다"). 이 문서의 일정표는 **4인 기준 하나뿐**이다. 3인이면 어디가 밀리고 5인이면 어디가 당겨지는지 추정하지 않았다.
→ **담당: 전원 / 시점: 팀 확정 직후 (13-1과 함께)**

### 그리고 조사 자체의 한계

**이 문서 자체는 독립 검증을 1회 받았고 지적 9건을 전부 반영했다**(머리말 참조). 그러나 **바탕이 된 조사 파일들은 아직 검증받지 않았다** — 별도 검증 절차를 거치지 않았고 미해소 정정 항목 4건이 남아 있다.

즉 **이 문서의 인용은 정확하지만, 인용된 조사 자체의 정확도는 별도 문제**다. 발표 전에 조사 검증까지 돌리는 것이 안전하다.
→ **담당: 팀장 / 시점: 발표 준비 전**

## 14. 역할 4개

### R1. 기획 · 상태 모델 설계 (PM 겸)

**이 자리가 제품의 심장이다.** 여기가 약하면 "AI 목표 앱" 하나 더 만드는 것으로 끝난다.

- 상태 필드 스키마 정의 — 목표가 무엇이든 담기는 하나의 틀
- 진단 질문 설계 · **Quest 판정 기준 설계** · 상태 전이 규칙
- LLM 프롬프트 작성·튜닝
- 시연 시나리오, 발표

**필요 역량**
- 필수: 제품 기획 경험, **LLM 프롬프트 작성 경험**, 문서화
- 우대: 운동·학습 등 단계적 트레이닝 설계 경험, **게임 기획 경험**

### R2. 백엔드 · AI 파이프라인

- LLM API 연동 — 진단 질문 / 경로 / Quest / 판정 기준 생성
- **구조화 출력 강제** — 상태 필드와 판정 기준을 스키마로 받기
- DB 스키마 — 상태 필드 + **변경 이력 테이블**
- 교정 트리거 및 경로 재계산

**필요 역량**
- 필수: Python(FastAPI) 또는 Node/Express, REST API 설계, **RDB 스키마 설계**
- 우대: LLM API 호출 경험, JSON Schema, Supabase

### R3. 프론트엔드

- **상태창** (홈 1급 화면) · 퀘스트창 · 온보딩 대화 UI
- 상태 값이 바뀌는 순간의 **연출** — 2차 시연의 임팩트가 여기서 결정된다

**필요 역량**
- 필수: React Native(Expo) 또는 Flutter, 상태 관리
- 우대: 애니메이션 · 게임 UI 감각, Figma 핸드오프 경험

### R4. 품질 · 데이터 + 디자인

- **시연 목표 사전 검증** — 여러 목표를 실제로 넣어보고 경로 품질 확인
- 상태 전이 규칙 테스트 케이스 작성
- UI 디자인 (RPG 톤, 상태창 시각화)

**필요 역량**
- 필수: 테스트 설계, 데이터 정리(Excel 또는 Python)
- 우대: Figma, UI 디자인
