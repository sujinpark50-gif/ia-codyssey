# I. 사업계획서

## 1. 한 줄로

> **목표를 세워주는 AI가 아니라, 내가 지금 어디에 있는지 알고 길을 찾아주는 AI.**
> 그리고 실제로 움직여본 결과로, 그 위치를 다시 계산한다.

**제품명(가칭)**: 미정 — 팀 합류 후 확정

---

## 2. 문제

목표 관리 앱은 이미 많다. 그런데 전부 같은 자리에서 멈춘다.

**"수학 공부하고 싶어요"라고 입력하면, 모든 앱이 똑같은 커리큘럼을 준다.**

고등학교 수학을 다 잊은 사람과, 미적분까지 했지만 선형대수만 모르는 사람에게 **같은 1주차**가 나온다. 그리고 3일 뒤 못 따라가면 앱은 이렇게 반응한다 — 일정을 뒤로 민다. 알림을 보낸다. 스트릭이 끊긴다.

**아무도 "왜 못 했는지" 묻지 않고, 아무도 "처음 판단이 틀렸을 수 있다"고 생각하지 않는다.**

사용자는 자기가 게으르다고 결론 내리고 앱을 지운다.

---

## 3. 해결 — 4단계 루프

| 단계 | 하는 일 | 화면 |
|---|---|---|
| ① **의도 → 목적지** | 막연한 말을 목표로 만든다 | 대화형 온보딩 |
| ② **현재 위치 진단** | 목표 대비 지금 어디인지 **측정**한다 | 진단 문항 + 짧은 테스트 |
| ③ **개인 경로 계산** | ①과 ② 사이를 잇는 경로를 만든다 | 퀘스트 목록 |
| ④ **실행 결과로 교정** | 실제로 해본 결과로 **②를 고치고 ③을 다시 만든다** | **상태창** |

**④가 이 제품의 전부다.** 나머지 셋은 이미 시장에 다 있다.

### 구체적으로

```
초기 진단: "함수 이해도 = 양호"   (사용자가 그렇다고 답함)
        ↓
Quest 수행: 함수 문제 3개 → 2개 오답
        ↓
상태 교정: "함수 이해도 = 양호 → 취약"   ← 시스템이 스스로 판단
           변경 사유: "함수 Quest 3회 중 2회 오답 (8/25)"   ← 저장됨
        ↓
경로 재계산: 다음 주차 앞에 함수 보강 3개 삽입
```

**사용자를 탓하지 않는다.** "계획을 못 지켰다"가 아니라 **"우리 초기 진단이 틀렸다"** 로 처리한다. 이게 슬로건이 아니라 데이터 구조로 성립한다.

---

## 4. 차별화 — 이 한 문장만 주장한다

> **자기보고된 현재 위치를 실행 결과로 교정하고, 그 교정 이력이 다음 경로 생성의 입력이 된다.**

이 문장이 성립하려면 세 가지가 **함께** 있어야 한다. 하나라도 빠지면 ChatGPT에 프롬프트 넣는 것과 구별되지 않는다.

| 조건 | 뜻 |
|---|---|
| **관찰의 자동성** | 실패를 사용자가 말해서가 아니라 **채점 결과에서** 검출한다 |
| **상태의 구조화** | 자유 메모가 아니라 **조회 가능한 필드** (`함수 이해도: 취약`, 변경 시각 포함) |
| **인과의 저장** | "왜 바뀌었는가"가 응답으로 스쳐가지 않고 **저장되어 나중에 조회된다** |

## 5. 시장 근거 (직접 조사, 2026-08 기준)

경쟁 제품 10개를 공식 자료 원문으로 조사해 14개 항목으로 비교했다.
대상: ATLVL · Attainify · Stepie · DAMI · Ripple AI · Goaltree · 키피 · Maty · Tiimo · 삼성 헬스 러닝코치

### 5-1. 이미 표준이 된 것 — 여기서 싸우면 안 된다

- **「목표를 단계로 쪼개준다」는 10개 중 10개가 한다.** 설치 10명짜리 개인 앱부터 삼성까지 전부.
- 자유 목표 입력 8/10, 목표 구체화 7/10.

**→ 이걸 차별화로 내세우면 즉시 무너진다.**

### 5-2. 비어 있는 것

- **미완료 "원인"을 구조화해 묻는 제품: 10개 중 0개**
- **목표 자체를 재검토하자고 제안하는 제품: 10개 중 0개**
- 확인된 재계획 트리거는 **전부 정량 신호**였다 — "3회 연속 스킵", "토요일 85% vs 금요일 30%", "부담스러워 보임". **"왜"를 입력으로 쓰는 제품은 없었다.**

### 5-3. ★ 가장 중요한 발견 — 진단과 교정이 한 제품 안에서 만나지 않는다

| 제품 | 진단 | 교정 | 빠진 고리 |
|---|---|---|---|
| **삼성 헬스 러닝코치** | **최고 수준** — 12분 실측으로 레벨 1~10 부여 | **없음** | 재측정이 수동이고, **재측정하면 기존 진행 이력이 삭제된다** (공식 문서 원문) |
| **Attainify** (설치 5,000+) | 있음 — 목표·경험·사고방식 퀴즈 | 모호 | 무엇을 관찰해 조정하는지 안 밝힘 |
| **Goaltree** | 없음 | **최고 수준** — 재계획 트리거 3개 공개 | 갱신되는 **상태 필드가 없다** |
| **Tiimo** | 사용자가 알려야 함 | **최고 수준** — 분해·이동 제안 | 행동 패턴 학습을 **공식 문서가 "아직 안 했다"고 밝힘** |
| ATLVL | 약함 | 중간 | 관찰값이 **무엇을 교정하는지** 서술 없음 |

**10개 전부 한 고리씩 빠져 있다. 예외 없다.**

### 5-4. 국내 상황

- 국내 직접경쟁 **3건** — DAMI(서울) / 키피(강남) / Maty(개인)
- **전부 초기 단계**: DAMI는 16개월 미갱신에 Google Play 리스팅도 내려감, 키피 설치 10+, Maty 설치 50+
- **한국어 정식 지원 확인은 4건**, **한국 특화 기능은 Maty의 사주 추천 1건**뿐

**→ 국내 시장은 아직 형성되지 않았다.**

## 6. 왜 「학습」 도메인인가

**진단을 하려면 측정할 수단이 있어야 한다.**

| 도메인 | 측정 수단 | 판단 |
|---|---|---|
| **학습 (수학 기초)** | **LLM이 문제를 내고 채점한다** | ✅ **채택** |
| 운동 | 워치·센서 필요 | ❌ 삼성이 이미 점유 |
| 창업·취업 | 없음 — 전부 자기보고 | ❌ "선언한 수준 vs 실제"의 대비 자체가 성립 안 함 |

**MVP는 학습 1개 도메인, 그중에서도 "AI 공부에 필요한 수학 기초" 하나로 좁힌다.**

추가 이유: **8주 안에 시연이 된다.** 운동이었으면 상태가 바뀌는 걸 보여주는 데 3일이 걸린다. 수학은 문제 3개면 된다.

## 7. 8주 MVP 범위

### MUST — 이게 없으면 제품이 아니다

1. **대화형 온보딩** — 막연한 목표를 받아 구체화
2. **진단** — 짧은 문항 + 진단 테스트로 **상태 필드 생성** (예: `함수 이해도`, `방정식`, `벡터` …)
3. **경로 생성** — 상태 + 목표 → 주차별 마일스톤 + Quest 목록
4. **Quest 실행** — LLM이 문제 3개 생성 → 자동 채점 (**1 Quest = 문제 3개**)
5. **상태 교정** — 채점 결과로 상태 필드 갱신 + **변경 사유 저장**
6. **경로 재계산** — 갱신된 상태로 다음 Quest 재생성
7. **상태창** — **홈 1급 화면.** 필드 값 + 변경 이력 + "왜 바뀌었는지" 조회

### SHOULD — 되면 좋다

8. 레벨·XP 표현 (RPG 감각)
9. 진단 이력 그래프
10. 목표 여러 개

### WON'T — 8주 안에 절대 안 한다

- ❌ **AI 안경** (완성형 비전, 지금은 안 함)
- ❌ 다도메인 (운동·취업 등)
- ❌ 소셜·파티·리더보드
- ❌ 캘린더 연동, 결제, 푸시 고도화
- ❌ **미이행 페널티** (HP 손실 등) — 이 제품이 명시적으로 안 하는 것

## 8. 시연 시나리오 — 심사에서 이 두 장면만 보여준다

### 1차 시연 (3분) — 이해용

> 세 명이 똑같이 **"AI 공부에 필요한 수학을 배우고 싶다"** 를 입력한다.
> → 앱이 **서로 다른 진단**을 한다.
> → **서로 다른 세 개의 경로**가 나온다.

**메시지**: "같은 목표라도 현재 위치가 다르면 경로도 달라야 한다."

### 2차 시연 (5분) — ★ 차별화 근거는 이것뿐

> 초기 진단에서 `함수 이해도 = 양호`로 잡힌 사용자가 함수 Quest를 푼다.
> → **3문제 중 2개 오답** (조작 없이 실제 채점)
> → **상태창의 값이 눈앞에서 바뀐다**: `양호 → 취약`
> → 그 항목을 누르면 **"왜 바뀌었는지"** 가 뜬다: "함수 Quest 3회 중 2회 오답 (8/25 14:32)"
> → **다음 주차 경로가 다시 만들어진다** — 함수 보강 3개가 앞에 삽입됨

**이 화면 하나에 세 조건이 전부 보인다** — 자동 관찰 / 구조화된 상태 / 저장된 인과.

**시연 시간 제약이 설계를 결정한다**: Quest 단위를 작게(문제 3개) 만들어야 5분 안에 상태가 바뀐다.

## 9. 8주 일정

| 주차 | 목표 | 산출물 |
|---|---|---|
| **W1** | **상태 모델 설계** + 화면 설계 + 스택 확정 | 상태 필드 스키마, 화면 와이어프레임 |
| **W2** | 온보딩 + 진단 → 상태 필드 생성 | 진단 동작 |
| **W3** | 경로 생성 (마일스톤 + Quest) | 1차 시연 가능 |
| **W4** | Quest 실행 — 문제 생성 + 자동 채점 | 채점 동작 |
| **W5** | **교정 로직** — 채점 → 상태 갱신 → 사유 저장 → 재계산 | **2차 시연 가능** |
| **W6** | 상태창·퀘스트창 UI 완성 + RPG 표현 | 화면 완성 |
| **W7** | 통합 + 채점 정확도 검증 + 리허설 | 안정화 |
| **W8** | 버그 수정 + 발표 준비 (**예비 주차**) | 최종 |

**W1의 상태 모델 설계가 가장 중요하다.** 여기서 스키마를 대충 잡으면 W5에서 전부 다시 짜야 한다.

## 10. 기술 구성 (제안 — 팀 역량 확인 후 확정)

| 영역 | 제안 | 비고 |
|---|---|---|
| LLM | **Claude API** (`claude-opus-5`) | 문제 생성·채점·경로 생성. 경쟁사 ATLVL도 Claude 사용 중 |
| 구조화 출력 | `output_config.format` (structured outputs) | **상태 필드를 스키마로 강제** — 자유 텍스트로 받으면 파싱 지옥 |
| 백엔드 | Python(FastAPI) 또는 Node | 팀 역량에 맞춰 |
| DB | PostgreSQL (Supabase 쓰면 빠름) | 상태 필드 + **변경 이력 테이블**이 핵심 |
| 프론트 | React Native(Expo) 또는 Flutter | 모바일이어야 RPG 감각이 산다 |

### 비용 추정 (개발 + 시연 기준)

| 모델 | 입력 $/1M | 출력 $/1M |
|---|---|---|
| Claude Opus 5 (`claude-opus-5`) | $5 | $25 |
| Claude Sonnet 5 (`claude-sonnet-5`) | $3 | $15 |
| Claude Haiku 4.5 (`claude-haiku-4-5`) | $1 | $5 |

- 개발 중 호출량은 크지 않다. **8주 전체 $30~80** 수준으로 예상 (호출당 수천 토큰 × 수천 회).
- **비용 절감 3가지**: ① 프롬프트 캐싱(상태 모델 프롬프트는 고정이라 캐시 잘 먹음) ② 채점처럼 단순한 작업은 Haiku로 분리 ③ 대량 배치는 Batch API(50% 할인)
- **예산은 리스크가 아니다.** 팀 카드 하나면 된다.

## 11. 리스크

| 리스크 | 대응 |
|---|---|
| **채점이 틀린다** | 수학 기초는 LLM 채점 정확도가 높은 영역. W7에 정확도 검증 주차 배정. 애매한 문제 유형은 제외 |
| **상태 전이 규칙이 어렵다** | 규칙을 단순하게 시작 — "3문제 중 2개 이상 오답 → 한 단계 하향". 정교화는 나중에 |
| **범용 LLM으로 환원된다** (가장 큰 위험) | ChatGPT에 같은 프롬프트를 넣고 **직접 비교 시험**을 한다. 우리가 이기는 지점은 **저장된 상태 필드와 변경 이력**이지 대화 품질이 아니다 |
| **W5에 몰린다** | W1 상태 모델 설계를 제대로 하면 W5는 연결 작업이 된다. W8을 예비로 비워둠 |
| 팀 역량 미스매치 | **아래 II장 모집으로 해소** |

# II. 팀 구성 및 모집

## 12. 역할 4개

### R1. 기획 · 상태 모델 설계 (PM 겸)

**이 자리가 제품의 심장이다.** 여기가 약하면 "AI 목표 앱" 하나 더 만드는 것으로 끝난다.

- 상태 필드 스키마 정의 (`함수 이해도`가 몇 단계인지, 무슨 근거로 바뀌는지)
- 진단 문항 설계 · 상태 전이 규칙 설계
- LLM 프롬프트 작성·튜닝
- 시연 시나리오, 발표

**필요 역량**
- 필수: 제품 기획 경험, **LLM 프롬프트 작성 경험**, 문서화
- 우대: 수학 기초 도메인 이해, 교육 서비스 경험

### R2. 백엔드 · AI 파이프라인

- LLM API 연동 (문제 생성 / 자동 채점 / 경로 생성)
- **구조화 출력 강제** — 상태 필드를 스키마로 받기
- DB 스키마 — 상태 필드 + **변경 이력 테이블**
- 교정 트리거 및 재계산

**필요 역량**
- 필수: Python(FastAPI) 또는 Node/Express, REST API 설계, **RDB 스키마 설계**
- 우대: LLM API 호출 경험, JSON Schema, Supabase

### R3. 프론트엔드

- **상태창** (홈 1급 화면) · 퀘스트창 · 온보딩 대화 UI
